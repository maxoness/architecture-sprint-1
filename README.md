# Задание 1. Уровень 1. Разделение проекта "Mesto" на несколько микрофронтендов. 

## Анализ проекта ##

### Бизнес анализ ###

Функиональность описана крупными блоками:
- Загрузка фотографий;
- Удаление фотографий;
- Сбор и учет лайков под фото;
- Создание профиля и его редактирование.

Можно представить её в виде трёх бизнес-доменов с соответствующими функциями:
- работа с пользователем:
    + регистрация;
    + редактирование профиля.
- работа с фотокарточками:
    + получение существующих;
    + создание;
    + удаление.
- социальное взаимодействие:
    + положительная реакция на карточку;
    + удаление положительной реакции на карточку.

### Технический анализ ###
Проект "Mesto" написан на JS-фреймворках.
Состоит из двух монолитных частей фронтэнда и бэкэнда.

#### Бэкенд ####
Написан на Node.js с использованием Express.

В бэкенде описаны две **модели**:
- Card;
- User.

Для работы с моделями в соответствующих контроллерах определы следующие **методы**:
1. ***Cards***:
    + getCards: получение всех карточек;
    + createCard: создание карточки;
    + deleteCard: удаление карточки;
    + updateLike: изменение карточки;
    + likeCard: положительная реакция на карточку;
    + dislikeCard: удаление положительной реакции на карточку.
2. ***Users***:
    + login: авторизация пользователя;
    + createUser: создание пользователя;
    + getUsers: получение всех пользователей;
    + getUserData: получение данных пользователя по ID;
    + getUser: получение данных пользователя по объекту пользователя;
    + getCurrentUser: получение данных текущего пользователя;
    + updateUserData: изменение данных пользователя согласно переданному объекту;
    + updateUserInfo: обёртка метода updateUserData для обновления общей информации о пользователе;
    + updateUserAvatar: обёртка метода updateUserData для обновления аватара пользователя.

Методы login и createUser в маршрутизаторе вынесены из домена Users на уровень выше.

#### Фронтэнд ####
Написан на React. 

В src/blocks размещены css-стили, декларирующие блоки элементов UI.
Замечу, что стиль фотокарточки включает в себя стиль для реакций-лайков.

В src/utils описаны API взаимодествия с сервисами бэкэнда:
- `auth`
  - `register`      / createUser
  - `login`         / login
  - `checkToken`    / getCurrentUser
- `general`
  - `getAppInfo` _`(getCardList + getUserInfo)`_ / getCards + getCurrentUser
- `cards`
  - `getCardList`   / getCards
  - `addCard`       / createCard
  - `removeCard`    / deleteCard
- `user`
  - `getUserInfo`   / getCurrentUser
  - `setUserInfo`   / updateUserInfo
  - `setUserAvatar` / updateUserAvatar
- `likes`
  - `changeLikeCardStatus::PUT`     / likeCard
  - `changeLikeCardStatus::DELETE`  / dislikeCard

## Проектирование ##

### Предварительный анализ и определение бизнес-функций ###
Приложение не слишком сложное и в текущем виде, в целом, могло бы работать и дальше. Но поставлена учебная задача разделения на микрофронты.

Выглядит, что достаточно воспользоваться **вертикальной нарезкой** вокруг озвученных в бизнес анализе доменов и, с учетом техических нюансов, выделить следующие **бизнес-функции**:
1. Auth (авторизация/регистрация пользователей)
2. Cards (работа с фотокарточками); _/* включая Social (социальное взаимодействие), т.к. при тех анализе выяснили, что UI реакций в едином блоке с фотокарточкой */_
3. Users (работа с пользовательскими данными);

Бизнес-функции Users и Auth разделены, т.к. персональные данные более чувствительны, чем данные для идентификации, а также это разные бизнес-сущности и хранятся отдельно (данные идентификации можно удалить, но клиент должен остаться).

Вокруг соответствующих доменов можно организовать 2-3 команды фронтэнд разработки (User и Auth можно отдать одной команде, т.к. могут быть "оборачивающие" обе сущености правила защиты, антифрода и т.д.).

Это также коррелирует с моделями бэкенда и в дальнейшем позволит также разбить его на соответствующие сервиса и организовать две-три **кросс-функциональные команды** вокруг эти бизнес-функций.
При дальнейшем развитии и усложнении проекта логично вынести Social (социальное взаимодействие) в отдельную вертикаль от UI до бэкенда.

Соответственно микрофронтенды и их бизнес и технические функции будут следующие:
1. **Auth**:
   - Регистрация пользователей
   - Авторизация пользователей
   - Проверка токена
2. **Cards**:
   - Отображение фотокарточек
   - Создание новых фотокарточек
   - Удаление фотокарточек
   - Функциональность лайков (как часть UI карточек):
        - Просмотр количества лайков
        - Добавление лайков
        - Удаление лайков
3. **Users**:
   - Отображение профиля пользователя
   - Редактирование профиля пользователя
   - Изменения аватара пользователя

4. **Host**:
   - Композиция микрофронтендов
   - Маршрутизация
   - Общий layout
   - Управление глобальным состоянием

Каждый микрофронтенд будет иметь собственный репозиторий, процесс сборки и развертывания, что позволит командам работать независимо друг от друга.

### Методы интеграции и композиции ###
Т.к. команд будет несколько, модули будут **разворачиваться независимо**.

Фронтэнд приложения интерактивный и фокус пользовательского опыта именно на интерактивности и графике, а значит идём в **клиентскую композицию** и текущий используемый JS-фреймворк React вполне подходит для сохранения в целевом решении, что также максимально задействует текущий опыт команды.

### Инструменты для создания микрофронтов ###
Исходя из полученного опыта в практической работе + целевого использования только React во всех микрофронтэндах (общие зависимости), предпочительными выглядит использование  **WebPack Module Federation**

### Управление состоянием ###
Для хранения данных авторизации пользователя потребуется **Глобальное состояние**. Можно использовать Redux, но в рамках учебного проекта достаточно использовать **Context API**. 
В будущем сюда можно будет добавить языковые настройки, настройки стилей и т.д.

Модель событий Pub/Sub могла бы потребоваться разве что для изменения отображения контента при изменении состояния авторизации, но ради этой одной функции достаточно "подписки" на изменения глобального состояния.

# Задание 2. Планирование разделения микросервисов
## Фронты
Предполагается два фронта: для клиентов и для внутренних пользователей (администраторы, тех поддержка).

Фронт для внутренних пользователей размещен только во внутренней сети, т.к. содержит интерфейсы для администраторов, имеющих доступ к корректирующим действия в критических мастер системах. Экрайны администраторов и тех поддержки разделены за счет разных ролей учётных записей.
## Маршрутизация
Для клиентских и администраторских фронтов используются разные сервера маршрутизаций, т.к. в случае сбоя на клиентском будет потом обращений от клиентов, который нужно уметь обслуживать независимо.
## Сервисы
### Сервис аутентификации
Контролирует учетки для доступа к сервисам: токены, учетные данные для авторизации (предполагается только по номеру телефона), роли доступа (внутренние/внешний пользователи, администраторы, тех поддержка)
### Сервис управления профилем
Управляет пользовательским профилем: регистрационные данные, статус (активные клиент, вип и т.д.)
### Сервис акционов
Управление аукционами разных типов: 1) на закупку товара 2) на оказание услуг 3) на продажу товара
Создание, ставки и т.д.
### Сервис заказов
Отправная точка для аукционов: заказ на нужные товары или услуги. Детали заказа, размещаемых на аукцион, статусы и т.д.
Цель заказа - получить по итогам аукциона товар/услуги по минимальной цене или финально продать товар/услугу по максимальной цене.
### Сервис товаров и услуг
Обратное плечо аукционов по отношению к заказам. По сути возможное предложение на заказ: товары и услуги.
Возможно размещение услуги или товара на аукцине. Тогда по итогам аукциона победит тот, кто предложит бОльшую цену и по ней будет сформирован заказ.
### Сервис платежей
Выставление счетов на оплату за заказы и проведение оплаты по ним через внешние платежные шлюзы
### Сервис генерации отчетов
Управление задачами на генерацию отчетов + сохранение финальных отчётов
### Сервис поддержки
Управление тасками от пользователей на обслуживание + аудит действий внутреннего персонала
### Сервис нотификаций
Управление шаблонами нотификаций, логирование отправки и отправка через шлюзы операторов
### Сервис поиска товаров и услуг
Получает от сервиса товаров и услуг соответствующих исходные данные, трансформирует и отгружает в elasticsearch.
Отвечает на поисковые запросы клиентов по товарам и услугам.
## Данные
Старую БД Постгре можно отдать сервису Аукционов, т.к. там будет больше всего соответствующих данных.
### Пользователи, профили и учетные данные
При изменении персональных данных пользователем в базе добавляется новая запись профиля с новыми данными и текущей датой актуализации, а предыдущая запись помечается как не актуальная для лучше селективности.
Аналогично с учетными данными, только дата актуальности здесь не нужна. 

Кроме того у пользователя может быть несколько профилей, привязанных к разным торговым площадкам (разные телефоны/емейлы для нотификаций), но при этом учетные данные для входа одни и те же.
Поэтому одной учетке соответствует один пользователей, но может соответствовать несколько профилей пользователей, но при этом пользователю может соответствовать несколько учеток (исторические).
### Отчеты
Данные для отчетов сливаются в единую аналитическую БД через топики Кафки, откуда их вычитывают обработчики сервиса отчетов.

Задачи на генерацию отчетов, а также сами сгенерированные отчеты прикапываются в Mongo DB, откуда могут быть повторно вычитаны по запросу.
## Поисковые данные
Для хранения информации про товары и услуги выбрана специализированная база ElasticSearch, в которую данные переливаются из мастер-сервиса "Товары и услуги" после предварительной трансформации сервисом "Поиска товаров и услуг".
### Аудит действий внутренних пользователей
Т.к. тех поддержка и администраторы могут делать корерктировки в критичных сервисах, все их действия сохраняются в отдельной базе Кассандры.
### Нотификации
Настройки маршрутизации и шаблонов хранятся в БД Постгре. Текущие назвершенные нотификации со статусной моделью в InMemory БД ApacheIgnite. История отправленных нотификаций - в кассандре.
В случае сбоя с InMemory события нотификаций могут переначитаны из партиций кафки.
## Потоки данных
### 1 Валидировать заявки на аппеляции
Администраторы принимают решения по аппеляциям и проводят соответствующие корректирующие действия в мастерсистемах, которые проксируются через Сервисы поддержки (в них доп логика лимитов, аудита и т.д.)
### Работа с заявками (регистрация, статус)
Помимо заявок с клиентских каналов связи, тех поддержка обрабатывает в том числе заявки, пришедшие с фронтов клиента.
### 3 Корректирующий действия в мастер сервисы
Изменить профиль, сгенерировать отчёт, изменить аукцион, заказ клиента и т.д.
### 4 Изменения учеток  пользователей
### 5 Заблокировать учетку, Установить роль
### 6 Учетные данные внутр пользователя для входа
Проверяются сервисом аутентификации и при успехе возвращается токен JWT
### 7 Учетные данные клиентов для входа
